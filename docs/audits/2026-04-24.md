# Audit bugs + points bloquants — 2026-04-24

## Contexte

Passe complète demandée par l'utilisateur : bugs, points bloquants, locks DB/écriture. Couverture Go backend (database/tx, services, handlers, middleware) + Preact frontend. 21 trouvailles dont 9 HIGH (concurrence writeDB, goroutines non bornées, shutdown racy), 8 MEDIUM, 4 LOW. SESSION-3 (Simkl import) droppée après clarification usage (one-shot sur DB vidée, sans webhook concurrent). Aucune injection SQL active ni faille d'auth critique : l'architecture writeDB/readDB + WriteDBTX compile-time est solide. Les risques réels sont de **starvation** et **failure modes silencieux**, pas de corruption.

**Méthode :** audit croisé 4 sous-agents + revue manuelle ; tous les findings ci-dessous ont été vérifiés à la source (3 faux positifs des agents écartés — voir section finale).

## BLOCKER / HIGH (10)

### ~~SESSION-1 — Shutdown racy : writeDB.Close avant drainage des workers — **HIGH**~~ — **DONE 2026-04-24**

~~**Risque :** À SIGTERM, `srv.Shutdown(5s)` draine les handlers HTTP, puis `Serve()` retourne et les `defer writeDB.Close()` / `readDB.Close()` s'exécutent. Mais `bgSvc.StartTicker` (ticker journalier) et `worker.Start` (task queue 30s poll) n'ont **aucun mécanisme de synchronisation** : ctx.Done leur est signalé, mais le retour de `Serve()` n'attend pas qu'elles finissent leur itération en cours. Transactions en vol → `database is closed` → tâches laissées en `status=running` (rescousées au redémarrage via `ResetRunning`, mais leur état disque peut être partiel).~~

**Fichiers :** `cmd/serve.go:37-38,101,109,134-138`, `internal/service/background.go:458-490`, `internal/service/taskqueue.go:88-140`

- [x] Ajouter un `sync.WaitGroup` partagé ; `StartTicker` et `worker.Start` font `wg.Add(1)` + `defer wg.Done()` ; `Serve()` appelle `wg.Wait()` avec timeout (ex. 10s) **après** `srv.Shutdown` et **avant** de retourner.
- [x] Vérifier que `triggerAsyncEnrichment` (plex.go:407) est inclus dans ce WaitGroup ou basculé vers la task queue (cf. SESSION-2).
- [x] `RefreshOne` handler (title.go:382) fire-and-forget → même WaitGroup.

**Implémentation :** WaitGroup injecté via `SetShutdownWG` sur `BackgroundService`, `TaskQueueWorker`, `PlexService`, `TitleHandler`. Nil-safe : les tests qui ne l'injectent pas conservent le comportement d'origine. `Serve()` attend jusqu'à 10 s puis log si dépassement.

### ~~SESSION-5 — Background ticker sans panic recovery — **HIGH**~~ — **DONE 2026-04-24**

~~**Risque :** Goroutine ticker journalière (`StartTicker` lignes 458-490) enveloppe `RefreshTitles`, `covers.FetchMissingCovers`, `covers.CleanupUnusedCovers`, mais **aucun `defer recover()`**. Panic dans n'importe quelle sous-étape = ticker mort silencieusement. Le daemon continue à tourner, mais les refresh cessent ad vitam. Symptôme : dernière entrée de log `background: starting scheduled refresh` puis rien ; aucune alerte.~~

**Fichiers :** `internal/service/background.go:458-490`

- [x] Envelopper le corps de la goroutine dans `defer func() { if r := recover(); r != nil { log.Printf("background: panic: %v", r); /* re-start après backoff */ } }()`.
- [x] Idéalement, pattern similaire à `taskqueue.go:112-139` : boucle externe qui relance après panic avec sleep 30s.

**Implémentation :** `StartTicker` enveloppe le corps de la goroutine dans une boucle externe `for { func() { defer recover() … }(); if ctx.Err() != nil { return } }`. Mirror exact du pattern `TaskQueueWorker.Start`. Panic → log + sleep 30s → re-entrée complète (startup delay + initial refresh + ticker). Coût acceptable vu la rareté du cas ; garantit que le daemon ne perd jamais sa boucle de refresh silencieusement.

### SESSION-7 — Push : 410 Gone traité en silence — **HIGH**

**Risque :** `SendNotification` (push.go:85-118) logge le status ≥ 400 mais retourne `nil`. Quand FCM/Mozilla renvoient 410 Gone (subscription expirée), on garde la subscription morte en base → tentatives répétées jour après jour → bruit log + quota API gaspillé. Pas non plus de `Retry-After` respect sur 429.

**Fichiers :** `internal/service/push.go:85-118`

- [ ] Sur `resp.StatusCode == 404 || 410` : appeler `s.Unsubscribe(ctx)` (lignes 74-78 — besoin d'un ctx ; actuellement `SendNotification` n'en prend pas → signature à étendre).
- [ ] Sur 429 : lire `Retry-After` et renvoyer une erreur retryable (cohérent avec `matching.ExtractRetryAfter`).
- [ ] Sur 5xx : retourner l'erreur au caller au lieu de `nil`.

### SESSION-8 — Google tokeninfo : pas de timeout HTTP — **HIGH**

**Risque :** `http.Get(...)` ligne 49 utilise `http.DefaultClient` qui n'a **aucun timeout**. Si l'endpoint `oauth2.googleapis.com/tokeninfo` stalle, le handler auth bloque sa goroutine indéfiniment. Rate limiter (10/min) mitige mais sur outage Google on peut saturer 10 handlers auth bloqués.

**Fichiers :** `internal/handler/auth.go:49`

- [ ] Définir un `var googleAuthClient = &http.Client{Timeout: 5 * time.Second}` au niveau package (pattern déjà utilisé dans `push.go:21`).
- [ ] Utiliser `googleAuthClient.Do(req)` avec un `http.NewRequestWithContext(r.Context(), ...)` pour propager aussi le ctx requête.
- [ ] Note sécurité (non-bloquant, hors scope) : migrer vers vérification JWT locale via JWKS Google plutôt que tokeninfo (endpoint legacy).

## MEDIUM (8)

### SESSION-11 — Order-by whitelist enforcée au handler, pas au repo — **MEDIUM**

**Risque :** `internal/repository/title_list.go:178` concatène `col := "t." + filter.Sort` directement dans la chaîne SQL. Injection impossible aujourd'hui car `internal/handler/title.go:49-57` check `allowedSorts[sortField]` avant d'assigner. Mais la protection est externe au repo : un nouvel appelant qui oublie la whitelist = injection. Défense en profondeur manquante.

**Fix :** dupliquer le whitelist dans `TitleRepository.List()` ou transformer `Sort` en type enum.

---

### SESSION-12 — Rate limiter : starvation sous attaque distribuée — **MEDIUM**

**Risque :** `internal/middleware/ratelimit.go:62-64` — quand map ≥ 10k IPs, tout nouveau IP est refusé. Sous attaque distribuée (botnet), un user légitime connecté depuis une IP fraîche prend 429. Devrait évincer l'entrée la plus vieille.

**Fix :** remplacer la map par un LRU (ex. `hashicorp/golang-lru`) ou trigger un cleanup immédiat quand la taille dépasse le seuil.

**Fichier :** `internal/middleware/auth.go:24-26`. `jwt/v5` valide `exp` par défaut, mais pas de tolérance pour skew horloge. Ajouter `jwt.WithLeeway(30 * time.Second)`.

**Fichier :** `internal/service/plex.go:82-85`. Kept for test compat selon le commentaire. Migrer les tests vers `ProcessWebhook(ctx, ...)` et supprimer la méthode.

**Fichier :** `frontend/src/store.ts:21-34`. Seulement `sort` persiste aujourd'hui, impact faible. Pattern à documenter pour les futurs caches : wrapper `{ ts, value }` + expiry 30 jours.

## Faux positifs écartés

- **Taskqueue enrichment tient la tx pendant les appels HTTP** (agent DB) — VÉRIFIÉ FAUX : `pipeline.Run` ligne 255 se termine AVANT `WithTxContext` ligne 277. La tx ne contient que des writes DB.
- **JWT expiry non validée** (agent handlers) — VÉRIFIÉ FAUX : jwt/v5 valide `exp` par défaut via le parser. Seul le leeway manque (cf. SESSION-19).
